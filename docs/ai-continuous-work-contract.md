# KEIBA LABO — AI共同作業の継続実行契約（提案）

## 目的
ユーザーがスクリーンショットを送る、同じ指示を繰り返す、AI間の伝言係になる状態をなくす。記録は成果物ではなく、次の実行を決める入力である。本書は既存のユーザー指示と安全制限を上書きしない。

## 毎回の開始ゲート（作業前必須）
1. Issue #178 の最新コメント、main の最新作業台帳、関連PR/commit、自然実行の直近receiptを確認する。古い記録と新しい記録が矛盾すれば時刻・実データ・証拠の強さで解決し、推測で上書きしない。
2. 「完了・進行中・未着手・外部公開待ち・承認待ち」を別々に記す。完了済み対象を再取得・再監査しない。
3. 既存承認の最優先対象、前回停止工程、次に実行可能な具体的変更を1つ選ぶ。実行できる作業があればユーザーへの再指示要求を禁止する。
4. 自然cron・403/lease/共有ゲート・D1上限・対象日照合・発走前LOCKの制約を継承する。強制取得、手動POST、直接DB操作、無断マージ/本番公開はしない。

## 自律的な工程遷移
- 実行可能なら「コード/データの作業→局所テスト→安全な差分→自然実行での実測→DB保存/独立GET/SHA/画面一致→次工程」を継続する。
- 原因が既知なのに調査・記録のみを繰り返すことは禁止。原因を直す変更を作り、レビューが必要ならPRで止める。
- 失敗時は「停止した工程・原因・既に試したこと・次の修正・再実行条件」を機械的に引き継ぐ。前工程に戻るのは新証拠があるときだけ。
- 取得がまだ公開されていない場合は、公開待ちとコード不具合を分け、次の自然処理を観測する。低優先処理へフォールスルーするならその分岐の修正を優先し、無限再試行・飢餓を防ぐ。

## 独立監視・連携
- 実装担当は作業の証拠（commit/PR、テスト、自然run ID、保存件数、GET/SHA）をIssue/台帳に残す。
- 監視担当はユーザーのスクショを待たず、GitHub記録と定期タスクから差分を確認する。報告の「成功」と実データの「保存成功」を分離し、停滞・優先逸脱・同一調査の反復を指摘する。
- 現時点で別チャットのWorkへ自動で指示が届く連携は未確認。Issue/PRを共通の作業受け渡し口とし、自動通知・実行の存在を偽らない。監視で見つけた阻害は具体的な修正単位にしてIssueに記す。実装担当は作業開始時に必ず確認する。
- ユーザーに求めるのは方針変更・高リスク操作・本番公開など必要な承認のみ。既承認の続きに再承認を要求しない。
