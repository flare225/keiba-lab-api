## 3. 最小構成

新規エンジンは `src/shared-page-acquisition.js`。本番entry pointからimportしていない。明示fetcher注入が必須で、誤って実ネットワークへ送るdefault fetchは持たない。

1. **ページ単位の共有**: 正規化URLを週scope内の共通キーにする。エンコード差を正規化するが、CNAMEを生成/補完しない。
2. **工程の分離**: 未取得→本文保存→解析→検証済みリンク共有→カード検証/保存。対象不一致・未公開・枠順未確定は別状態。
3. **途中再開**: 本文とreceipt pointerをatomic batch保存。解析失敗・応答喪失後は同じSHAの本文を読み、外部0で再開。解析版が変わるまで同じ壊れた解析を自動反復しない。
4. **期限優先**: 発走近い対象を先にし、個別待機は除外。非urgentの遠い対象は6時間のage上限を持つローカル案で機会を救済。urgent飽和・共有停止時の有限待ち保証はしない。この値は本番承認済みの設定ではない。
5. **既存成果の保持**: 個別URLは確認済み識別を保持して使い回す。古い親ページの再取得より、既知の子ページへの継続を先にする。正式完成レースは再取得しない。
6. **保存不確定の回収**: カードが既に保存されていた場合、source SHA・runner SHA・番号/枠・騎手/斤量/性齢・時刻の一致を読取で確認する。同一版なら回収0新規、異なる版なら上書きせず停止。
7. **予想と分離**: カード保存や本文キャッシュを予想保存/LOCK成立として数えない。枠順未確定ページは新キャッシュ版として保持し、既存の想定/枠順未確定表を勝手に上書きしない。

## 9. 保存容量と安全な運用期間

ローカル再生の72R本文は、平坦34,015bytes・中間階層34,658bytes。架空2頭カードの小さなfixtureであり、本番容量の根拠にはできない。受信生byte容量と保存するデコードUTF-8容量は一致を保証しない。

以下は**推定シナリオ**。72カード+9ナビゲーションページ、ナビ各32KiB、各URL1版と仮定する。実HTMLからの計測ではない。

| 平均カード本文 | 週あたり新本文 | 16MiB上限との関係 |
| --- | ---: | --- |
| 64KiB | 4.78125MiB | raw予算内。ただしmetadata/index別 |
| 128KiB | 9.28125MiB | raw予算内。ただしmetadata/index別 |
| 256KiB | 18.28125MiB | raw予算超過、72R前に停止 |
